# Roadmap v4.0 - Overhaul AI Architecture

## Overview

Replace AI-invented recipes with database-grounded meals from Spoonacular, implement a lazy-save draft workflow, and consolidate all LLM calls through a shared client with enforced token controls. The build order follows strict dependency chains: shared modules and database migrations first, then Spoonacular integration and AI coordinator, then lazy-save draft workflow, then UI and safety polish, and finally cleanup of deprecated functions.

## Phases

- [ ] **Phase 13: Foundation & Database Migrations** - Shared AI client, DB schema extensions, recipe cache table, bulk save RPC
- [ ] **Phase 14: Spoonacular Integration & AI Coordinator** - Recipe search Edge Function, AI coordinator directives, quota tracking, allergen taxonomy
- [ ] **Phase 15: Lazy-Save Draft Workflow** - Draft state management, slot operations in memory, explicit save/discard, localStorage backup
- [ ] **Phase 16: UI Updates & AI Safety** - RecipeDetail dual mode, source attribution, draft controls, aisle shopping list, allergen scan, fallback labeling
- [ ] **Phase 17: AI Adapter & Cleanup** - Recipe adaptation Edge Function, deprecate ai-proxy, remove categorize-ingredients, replace old pipeline

## Phase Details

### Phase 13: Foundation & Database Migrations
**Goal**: All infrastructure exists for new Edge Functions and recipe data to flow through the system
**Depends on**: Nothing (first phase of v4.0)
**Requirements**: INFRA-01, INFRA-02, INFRA-03, INFRA-04, INFRA-05, INFRA-06
**Success Criteria** (what must be TRUE):
  1. A new Edge Function can import `_shared/ai-client.ts` and make an LLM call with role-based temperature and max_tokens without duplicating provider logic
  2. Every LLM call made through the shared client produces a token usage log entry visible in the database
  3. The `recipe_cache` table accepts Spoonacular JSONB data with GIN-indexed queries returning results under 50ms
  4. The `recipes` table can store source_provider, source_id, and image_url for grounded recipes
  5. The `save_meal_plan_bulk` RPC function atomically inserts a full week of meals, recipes, and shopping list items in a single transaction
**Plans**: 3 plans

### Phase 14: Spoonacular Integration & AI Coordinator
**Goal**: Users can generate meal plans grounded in real Spoonacular recipes with quota-aware search and automatic fallback
**Depends on**: Phase 13
**Requirements**: SEARCH-01, SEARCH-02, SEARCH-03, SEARCH-04, SEARCH-05, SAFE-05
**Success Criteria** (what must be TRUE):
  1. User can trigger meal generation and receive real Spoonacular recipes with verified nutrition data, ingredients, and aisle information
  2. The AI Coordinator produces structured search directives (query, diet, cuisine, allergen exclusions, calorie range) that the recipe-search function consumes
  3. User can configure how many meals to generate (e.g., 7 instead of 21) for partial plan generation
  4. User can see current Spoonacular quota usage and the system automatically falls back to AI generation when quota reaches 80%
  5. Allergen exclusions use a structured taxonomy mapping categories to specific ingredients (not substring matching)

### Phase 15: Lazy-Save Draft Workflow
**Goal**: Users review and curate generated meal plans in memory before any database writes occur
**Depends on**: Phase 14
**Requirements**: SAVE-01, SAVE-02, SAVE-03, SAVE-04, SAVE-05, SAVE-06
**Success Criteria** (what must be TRUE):
  1. After generation completes, the user sees a draft meal plan in the planner UI with no rows written to the database
  2. User can delete, refresh, lock, and edit individual meal slots entirely in draft mode without triggering any database calls
  3. User can click "Save This Plan" to persist the entire draft atomically, or "Discard" to throw it away with zero database side effects
  4. If the user refreshes the browser with an unsaved draft, the draft is restored from localStorage (within 24 hours) with a prompt to continue or discard
  5. User is warned via browser prompt before navigating away with unsaved changes

**UI hint**: yes

### Phase 16: UI Updates & AI Safety
**Goal**: Users can distinguish grounded vs AI-generated recipes, view drafts and persisted plans through appropriate UI treatments, and trust that allergen violations are caught programmatically
**Depends on**: Phase 15
**Requirements**: UI-01, UI-02, UI-03, UI-04, SAFE-01, SAFE-03, SAFE-04
**Success Criteria** (what must be TRUE):
  1. RecipeDetail view works in both draft mode (reading from React state) and persisted mode (reading from DB) with full ingredient and instruction display
  2. Grounded recipes show "Recipe from Spoonacular" attribution and a verified nutrition badge; AI-generated fallbacks show a distinct "AI-Generated" badge on both the meal card and detail view
  3. Draft mode displays Save/Discard controls and a "Draft" indicator; persisted mode hides these controls
  4. Shopping list uses Spoonacular aisle categories for grouping instead of the LLM categorizer
  5. After plan assembly, a programmatic scan checks all recipe ingredients against household allergen profiles and flags violations before the user can save
**Plans**: TBD
**UI hint**: yes

### Phase 17: AI Adapter & Cleanup
**Goal**: Recipes can be adapted for allergies/serving size via AI, and all deprecated Edge Functions are removed
**Depends on**: Phase 16
**Requirements**: SAFE-02, CLEAN-01, CLEAN-02, CLEAN-03
**Success Criteria** (what must be TRUE):
  1. When a grounded recipe has allergen or serving-size conflicts, the AI Adapter produces a modified version with substitutions (not a newly invented recipe) and the adaptation is recorded in the data
  2. The `ai-proxy` Edge Function is removed and all former callers use the shared AI client
  3. The `categorize-ingredients` Edge Function is removed and shopping list grouping uses provider aisle data exclusively
  4. The `generate-plan` and `refresh-slot` Edge Functions are replaced by the new select-meals/recipe-search pipeline
